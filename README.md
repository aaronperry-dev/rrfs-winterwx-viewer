# RRFS winter-weather dashboard · New England

A static GitHub Pages dashboard for the NOAA **Rapid Refresh Forecast System (RRFS) ensemble** over New England, built around
everything that matters in a winter storm: QPF, snowfall by four ratio methods, freezing rain and sleet, precipitation type,
dendritic-growth-zone (DGZ) diagnostics, lift, wind, visibility, blizzard criteria and wind chill.

It looks and behaves like the sibling RTMA/URMA viewer (same layout, colours, station values and map furniture), and is
regenerated by GitHub Actions a few times a day. **No data is ever committed to git**: each run builds the site in a scratch
directory and deploys it as a Pages artifact.

## What you can do on the page

| Control | What it does |
|---|---|
| **Topic / Product** | 7 topics, 25 products (table below). |
| **Ensemble view** | `RRFS Mean (REFS)` · `Member mean` · `Spread (σ)` · `Minimum` · `Maximum` · `Probability`. |
| **Members** | Click `m001`–`m005` to switch members **on or off**; mean, spread, min, max and probabilities are recomputed instantly in your browser from the members left on. |
| **Single member** | Look at one member on its own. |
| **Probability of** | Threshold buttons per product (e.g. ≥ 6 in of Kuchera snow, ≥ 0.25 in QPF, ≥ 50 mph gust, ≤ 0 °F wind chill). |
| **Accumulation window** | Run total, or any 3/6/12/24-h window of an accumulation (computed by differencing stored totals). |
| **All members** layout | Postage-stamp grid: REFS mean, member mean, spread, probability and every member side by side. |
| **Time** | Slider, ◀ ▶ buttons, ← / → keys, space to play; valid times in UTC and Eastern. |
| **Click the map** | Point forecast: every member, the member mean and the REFS mean as lines over the forecast. |
| Hover | Value under the cursor. Land-area low / average / high tiles for the current map. |

The URL hash stores the state (`#snow_kuchera/mean/12/0/map`), so a view can be bookmarked or shared.

## Products

| Topic | Product | How it is made |
|---|---|---|
| Precipitation | **QPF** | Sum of hourly `APCP` (members) · REFS mean `APCP` |
| Snowfall | **Model snowfall** | RRFS `ASNOW` run total (the model's own variable ratio; includes sleet) |
| | **10:1 snowfall** | Snow-type liquid × 10. Snow-type liquid = hourly `APCP` × precipitation-type flag (`CSNOW`) |
| | **Kuchera snowfall** | Snow-type liquid × Kuchera ratio, `12 + 2 (271.16 K − Tmax)` for Tmax > 271.16 K, `12 + (271.16 K − Tmax)` otherwise, Tmax = warmest temperature from 2 m up to 500 hPa; ratio clipped to 3:1–40:1 |
| | **Max-T-aloft snowfall** | Snow-type liquid × 5th-degree polynomial in the warmest temperature from ~610 m AGL to 500 hPa (Veals et al. 2025) |
| | **Kuchera / Max-T-aloft ratio** | The ratios themselves, at the valid time |
| Ice & p-type | **Freezing rain, sleet** | Hourly `APCP` × `CFRZR` / `CICEP` flag (liquid equivalent) |
| | **Snow / sleet / freezing rain / rain** | Precipitation-type probability (members: 0 or 100; mean: % of members) |
| | **Warm nose** | Warmest temperature 925–700 hPa |
| Snow growth (DGZ) | **DGZ depth** | Depth (hPa) of the layer between −12 °C and −18 °C, from linear interpolation between pressure levels |
| | **Saturated DGZ depth** | The part of that layer where layer-mean RH with respect to ice ≥ 100 % |
| | **DGZ mean RH (ice)** | Pressure-weighted RHi inside the DGZ |
| | **Peak upward motion** | `MAXUVV` (hourly max vertical velocity, 100–1000 hPa); the lift proxy, see limitations |
| Wind & blizzard | **Gust, wind speed, visibility** | `GUST`, `UGRD`/`VGRD`, `VIS` |
| | **Blizzard conditions** | Wind **or** gust ≥ 35 mph **and** visibility ≤ ¼ mi **and** snow or sleet falling |
| | **Blizzard duration** | Longest run of blizzard samples so far (the NWS criteria need ≥ 3 h) |
| Temperature | **2 m temperature, wind chill** | `TMP`; NWS wind-chill formula (T ≤ 50 °F, wind > 3 mph) |

Colour ramps are fixed physical bins (a colour always means the same value in every frame and for every member). Wind and
wind-chill legends are the same NWS-style ramps as the RTMA dashboard.

## Data and the "lean fetch"

* Bucket `noaa-rrfs-ops-pds` (anonymous, `us-east-1`):
  * members `rrfsens.YYYYMMDD/CC/m00N/rrfs.tCCz.m00N.{2dfldnomads,prslevnomads}.3km.fFFF.conus.grib2`
  * REFS mean `refs.YYYYMMDD/CC/ensprod/refs.tCCz.mean.fFF.conus.grib2`
* Every GRIB2 file has a `.idx` sidecar. The code reads it (a few kB), finds the byte range of each needed message and issues one
  HTTP `Range` request per field, a ~1–2 MB message instead of a multi-hundred-MB file. Messages are decoded from memory with
  `eccodes`; nothing is written to disk.
* Per member and 3-hourly frame: 3 hours of `APCP` and type flags, `ASNOW`, 2 m / 10 m fields, `GUST`, `VIS`, `PRES`, `MAXUVV`,
  `TMP` on 11 pressure levels and `RH` on 8 → roughly 75 requests including index files. The five members and the REFS mean run in parallel processes.
* The newest cycle (00/06/12/18 UTC) whose **last forecast hour (F060)** exists for the REFS mean and every member is used.
* Fields are re-projected from the 3 km Lambert grid onto a fixed New England raster (3 km, nearest neighbour, indices
  pre-computed and cached), then quantised (8/16 bit) and gzip-compressed per product and source. The browser decodes them with
  the native `DecompressionStream`; 8-bit fields are stored as a 2-D delta, 16-bit fields byte-shuffled, which roughly halves the
  gzip size.

### Why the member mean is computed in the browser

The page needs to be able to switch members on and off. Pre-rendering every combination would be 2⁵ × products × frames images,
which is far too much for GitHub Actions and Pages. Instead the server stores one compact file per product and member, and the
browser reduces whichever members are switched on. That keeps the build small, makes any combination instant, and means no
re-computation of products on the server.

### REFS mean vs. the member mean

They are not the same thing. NOAA's REFS mean is computed over **all** REFS members (the 12 RRFS members, plus time-lagged members and two HRRR members), but only
five members are on S3 and the dashboard's member mean covers only those. The REFS mean file also carries far fewer fields than the
members (no gusts, no pressure-level profiles). Fields it lacks are shown as unavailable in the `RRFS Mean (REFS)` view and
fall back to the member mean with a notice.

## Size

Measured on the offline demo (455 × 293 display grid, 3 frames, 6 sources): 8.4 MB of data files + a 46 kB overlay. Scaled to the 20
frames of a full run that is roughly 55 MB for the whole site (synthetic fields; real fields may compress differently), and a
visitor downloads only the product being viewed: about 3–6 MB for all six sources, cached afterwards.
What a build **downloads** from S3 is much larger than what it publishes (every needed message at full CONUS resolution); the
demo transferred ≈ 50 MB per member for 3 frames, and the real grid is about 7× larger. Expect several GB per run, which is
free on a public repository but is the main thing to check in the first live log.

## GitHub Actions limits

Designed so that scheduled generation is never stopped by GitHub:

* The repository is **public** (Actions minutes are free), runs finish in minutes, the job has a hard `timeout-minutes`, and a
  `concurrency` group prevents overlap.
* Data is never committed; the site is built in the runner and deployed with `upload-pages-artifact` + `deploy-pages`. The
  deployed site is on the order of 50 MB (see *Size*), far under the 1 GB Pages limit, and the repo itself stays tiny.
* Runs are scheduled after each cycle and twice more for slow cycles. A run that finds the site already showing the newest complete cycle
  exits in about a minute without deploying (`--skip-if-deployed`).
* GitHub disables scheduled workflows in public repos after 60 days without repository activity. A best-effort step re-enables
  the workflow on every run. If scheduled runs stop anyway, push any commit or press *Run workflow*.

## Set up

1. Create a public repository, e.g. `rrfs-viewer`, and push this folder.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
3. **Actions → Update RRFS winter dashboard → Run workflow** (tick *force* the first time).

The site appears at `https://<user>.github.io/<repo>/`.

## Run it locally

```bash
pip install -r requirements.txt
python -m rrfs_viewer.build --out public                      # real data, newest complete cycle
python -m rrfs_viewer.build --demo --max-fhr 12 --out public   # offline: synthetic storm via a fake S3 bucket
python -m http.server -d public 8000
pytest
```

`--demo` serves real GRIB2 messages with a correct `.idx` from an in-process fake bucket (`rrfs_viewer/testing.py`), so the
whole production path (index lookup, byte ranges, decode, derive, encode) is exercised without network access. The meteorology
in demo mode is synthetic and marked as such on the page.

## Limitations: read before trusting a number

* **Not yet validated against the live bucket.** The field names and `.idx` descriptors (`APCP` 1-hour windows, `ASNOW` totals, `MAXUVV`,
  `VIS`, pressure-level `TMP`/`RH`) follow the published RRFS/REFS product tables and the layout of comparable NCEP files; they were
  developed offline. Missing messages are not fatal: the product is simply empty for that frame/member (a hole in the hourly
  `APCP` withholds all later accumulations rather than under-reporting them), and the Actions log lists what was missing.
* **No Cobb SLR.** It needs omega on pressure levels, which the RRFS files don't carry. `Peak upward motion` (`MAXUVV`, a column maximum)
  is a proxy for lift and cannot say *where* in the column the lift is relative to the DGZ.
* **Max-T-aloft ratio is experimental.** The polynomial was fitted to Alaska observations and is untested for New England;
  treat it as one more scenario next to Kuchera, 10:1 and the model's own `ASNOW`. The pressure-level data stops at 500 hPa.
* **Kuchera** uses the 2 m temperature and levels up to 500 hPa (the original used the surface-to-500 hPa layer as well).
* **DGZ RH** exists only at 925–500 hPa, so DGZ layers below 925 hPa count as "unknown" and not as saturated.
* **Freezing rain and sleet are liquid equivalents.** No radial-ice/flat-ice accretion model is applied.
* **Blizzard** uses the model's visibility (no blowing snow) and 3-hourly samples: two consecutive qualifying samples are taken
  to span 3 hours. Treat it as guidance for where criteria are plausible.
* The member mean covers m001–m005 only; the control member is not on S3.
* Precipitation type is the model's categorical flag (0 or 1) at the valid time; hourly flags are averaged between consecutive hours when
  splitting accumulations by type.

## Layout

```
rrfs_viewer/
  config.py      bucket layout, cycles, frames, display area
  s3.py          anonymous boto3, .idx parsing, one byte-range request per message
  grib.py        eccodes decode, native -> display raster mapping
  winter.py      SLR methods, DGZ, warm nose, RHi, wind chill, blizzard
  pipeline.py    per-member and REFS processing -> (frames, ny, nx) products
  catalog.py     the product list: units, quantisation, thresholds, text
  colors.py      colour ramps (OKLab)
  encode.py      quantise, delta/shuffle, gzip
  basemap.py     cartopy overlay (boundaries, frame), land mask, METAR layout
  build.py       cycle choice, parallel workers, data.json, site assembly
  testing.py     offline fake S3 with real GRIB2 (demo + tests)
site/index.html  the dashboard (single file, no dependencies)
.github/workflows/update.yml
```
